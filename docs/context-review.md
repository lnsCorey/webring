# Agent context review

A review of the project's agent context (`CLAUDE.md`, `AGENTS.md`, `.agents/`, `.claude/`): whether it makes sense, where it contradicts itself, and where it disagrees with the code. It's meant as input for rewriting the context.

> **Edit the source, not these files.** `CLAUDE.md:3` says: *"Generated by AI La Carte. Edit the library, not this file: changes here are overwritten on deploy."* Make the rewrite in the AI La Carte library, or the next deploy will undo it.

## 1. Summary

- **The mission holds up.** "Local client is the engine, the public profile is a static artifact, peers exchange signed static JSON, federation is local aggregation" describes Webring Studio accurately.
- **The rules and roles describe a different system:** a live P2P network with bootstrap nodes, gossip, NAT traversal, CRDT replication and ActivityPub server-to-server. None of that exists, and much of it contradicts the mission.
- **The context is producing bad advice.** The earlier "Architectural Consistency Analysis" was organized as an *Architect's*, a *Protocol Specialist's* and a *UX Strategist's Mandate*. Those are the three roles defined here. It assumed CRDT merges, JSON-LD and public-key moderation because these files told it to.
- **Recommendation:** keep the mission. Rewrite the rules and roles around the model the code actually uses: pull-based, did:web, signed static JSON. Collapse the duplicated files into one source of truth, and add the practical project facts the context is missing (commands, layout, conventions).

## 3. Structure and format problems

1. **The mission text appears three times,** word for word: `CLAUDE.md:5-22`, `AGENTS.md:5-24`, and the intent file. Every copy is another place for edits to drift.
2. **The rules and roles exist twice.** `.claude/rules/*` and `.agents/rules/*` are identical except for frontmatter; the same goes for `.claude/agents/*` and `.agents/roles/*`. Claude Code reads only `.claude/`, while other agent tools read `AGENTS.md` and `.agents/`. Keep one source. A common pattern is a full `AGENTS.md` plus a `CLAUDE.md` that contains `@AGENTS.md` and any Claude-only notes.
3. **`AGENTS.md:61-69` "Assembly Instructions for the Harness" describe a loader that doesn't exist.** They refer to "context blocks", "memory objects" and "expose tools to the agent according to their schemas". No agent tool follows these steps, so they only cost tokens.
4. **`AGENTS.md:77` "The agent must cite which role or rule governs a decision"** makes every answer longer without improving decisions. Drop it.
5. **Labels don't match:**
   - The same list is called "KPIs" in `AGENTS.md:19` and "Success criteria" in `CLAUDE.md:17`. Neither is measurable; they're benefits. "Why this architecture" would be a more honest heading.
   - Frontmatter `type` values are inconsistent: `intent`, `Role`, `Rule`.
6. **Leftovers from splitting one long document:**
   - Rule headings keep their old section numbers ("### 1. Core Philosophy", "### 2. Architecture", and so on).
   - `security-moderation.md` has no heading at all.
   - The protocol role starts with "## Persona 2: The Protocol & Security Specialist".
7. **A broken list item:** `-g   **Moderation & Governance:**`, at `.agents/roles/the-ux-product-strategist.md:12` and `.claude/agents/the-ux-product-strategist.md:14`. The stray `g` breaks the Markdown list.
8. **The subagents don't work well as subagents:**
   - Claude Code picks a subagent from its `description`. These read "As a … your focus is …" rather than "Use when …", so it can't tell when to delegate.
   - They carry no repo facts, no `tools` restriction and no expected output, so they give generic textbook advice.
   - They're expertise lists ("Your expertise includes: P2P topologies, DHTs…"), not task instructions.
9. **All five rules load in every session** because none has `paths:` frontmatter. That's acceptable at this size. Once rewritten, the SSG/publishing rule could be scoped to `electron/services/siteGenerator.ts` and `electron/services/publisher.ts`.
10. **Greenfield wording in a codebase that already exists:**
    - "Propose and refine this schema as a first step" (`architecture-data-model.md:12`): the schema already exists as zod schemas in `src/shared/schema.ts`.
    - "Markdown files with JSON frontmatter, or a local database like SQLite" (`architecture-data-model.md:13`): SQLite has already been chosen.
    - "Implement a robust mechanism for discovering other peers" (`p2p-federation-networking.md:11`): reads like a to-do item, not a rule.

## 5. Context vs. code

| Topic | What the context says | What the code does |
|---|---|---|
| Peer exchange | Bootstrap nodes, gossip, peer connections, NAT traversal | Pull-only, on-demand HTTP fetch of a friend's `/api/*.json`. No bootstrap list, gossip, sockets or timers (`electron/services/ringCrawler.ts`). Matches the mission, not the rules. |
| Identity | The public key is the identifier; add peers by key or invitation code | did:web from the site URL (`siteUrlToDidWeb`, `src/shared/schema.ts`) plus an Ed25519 key pinned on first use. Friends are added by **site URL**. |
| Replication | CRDTs, or last-write-wins by timestamp + peer ID | Each entry has one author; the newest fetch replaces the row, keyed by canonical URL. No timestamps or peer IDs used for ordering. |
| Webring | Replicated CRDT; Next / Previous / **Random** links | A hub JSON file determines prev/next (`RingCrawler.syncWebringHub`). The site shows Prev and Next only; **there is no Random link**. |
| Moderation | Keyed by public key; filtered during sync and generation | Keyed by **site URL** (`moderation` table, `electron/db/database.ts`). Mute hides from the local feed only. Block skips crawling and keeps that site's endorsements out of the export. |
| Static HTML | "Core content must be rendered as static HTML" | `index.html` builds its content in the browser from inline JSON via `root.innerHTML` (`electron/services/siteGenerator.ts:562`). Content is invisible without JavaScript. |
| Deploy targets | IPFS, S3, ZIP | Local folder, SFTP/FTP, GitHub Pages (`electron/services/publisher.ts`). None of the listed targets exist. |
| Third-party services | "Avoid any reliance on centralized servers" | The public site can load Tailwind CDN, Giscus/Utterances (GitHub), Google Analytics and AdSense (`siteGenerator.ts:205-248`). They're client-side, so "no server-side" allows them, but no rule says when they're acceptable. |
| Private key | Encrypted at rest; never leaves the device | Encrypted with the OS keychain via `electron/security/keyVault.ts` (new, uncommitted). The key is never exported. Holds. |
| Data format | JSON-LD / ActivityPub compliance | Custom zod-validated JSON. Only `did.json` is JSON-LD. Signatures use a custom canonicalization (see `docs/architecture/federation.md`). |

### Not mentioned anywhere in the context

- **The MCP server:** the stdio CLI, plus a loopback HTTP/SSE endpoint inside the app (`electron/mcp/`). AI agents can create posts, crawl and publish through it.
- **Personas:** each has its own database, key, media folder and export path (`electron/services/personaManager.ts`). This is a core privacy feature with no rule protecting it.
- **ATProto:** handle and PDS entry in the DID document.
- **`webring://` deep links.**
- **Add-ons:** analytics, ads, comments.
- **The architecture doc:** `docs/architecture/federation.md`, written last session to define the internal-state / curated-view / exchange-format boundaries.

### Security gap the rewritten security rule should cover

The in-app MCP HTTP server sends `Access-Control-Allow-Origin: *` and has no authentication (`electron/mcp/mcpHttpServer.ts:34`). It only listens on 127.0.0.1, but any web page open in the user's browser could call it, including its signing and publishing tools, once it finds the port. The current rules say nothing about local automation surfaces.

## 6. Missing practical context

The context is all philosophy. It has none of the facts an agent needs to work in this repo:

- **Commands:**
  - `npm test` (vitest)
  - `npm run dev` (build, then launch Electron)
  - `npm run build:electron`
  - `npm run mcp` (stdio MCP server)
- **Native-module gotcha:**
  - Electron 33 uses `better-sqlite3`, compiled for Electron (`npm run rebuild:electron`).
  - Tests and the MCP CLI on Node 22+ use built-in `node:sqlite`.
  - Running `rebuild:node` breaks the app until you rebuild for Electron again.
- **Layout:**
  - `electron/main.ts` and `preload.ts`: IPC.
  - `electron/db/database.ts`: SQLite and the signed bundle.
  - `electron/services/`: crawler, generator, publisher, personas.
  - `electron/mcp/`, `electron/security/`.
  - `src/shared/schema.ts`: zod schemas, signing, did:web.
  - `src/studio/App.tsx`: studio UI.
  - `src/profile-site/`.
  - `tests/federation.test.ts`.
- **Conventions:**
  - The zod schemas in `src/shared/schema.ts` are the data contract.
  - Everything published goes through `buildSignedSiteBundle()`.
  - Peer data is read only through the curated view (`getCuratedNetworkFeed` / `getCuratedEndorsements`).
  - Schema changes are additive (`CREATE TABLE IF NOT EXISTS` / guarded `ALTER TABLE` in `initializeSchema`).
  - Federation behaviour gets a test in `tests/federation.test.ts`.
- **Known state:** `src/studio/App.tsx` has 6 TypeScript errors that predate recent work (TS2783: default publish settings in `refreshStudioData` are overwritten by a later `...p.publishSettings` spread).

## 7. Recommended target structure

**Files**
- **`AGENTS.md`** (single source): the mission (once), a short "how it actually works" section, commands, layout, conventions, and a link to `docs/architecture/federation.md`.
- **`CLAUDE.md`:** `@AGENTS.md` plus Claude-only notes, if any.
- **Rules:** one copy, in whichever folder the generator targets. Rewrite them as:
  1. **Static artifact.** The public site is static files only. Core content should render without JavaScript (*decision needed, see below*). Third-party scripts only as opt-in add-ons, off by default.
  2. **Pull federation and identity.** did:web plus an Ed25519 key pinned on first use. Peers are added by site URL. Sync means fetching signed static JSON. No live connections.
  3. **Signing and verification.** Every published document is signed. Unverified peer data is never re-published. Only verified fetches may delete local data.
  4. **Moderation.** Keyed by site URL. Mute = local feed only. Block = don't crawl, and don't publish their endorsements.
  5. **Local state and automation.** SQLite per persona. Personas never share data. The MCP CLI and HTTP endpoint are trusted local surfaces and must not be reachable from web pages.
  6. **Publishing.** Generate, then deploy (local folder, SFTP/FTP, GitHub Pages). Each publish records a snapshot time.

**Roles**
- Either drop them, or narrow each to this repo with a "Use when …" description, a tools list and an expected output.
- Remove DHT, Gnutella, NAT traversal, gossip, DMs, E2E encryption and Sybil/eclipse topics, unless they're actually planned.
- Examples:
  - **Protocol & security reviewer:** use when changing signing, verification, TOFU pinning, the export surface or MCP endpoints.
  - **UX reviewer:** use when changing studio flows such as onboarding, sync, publish and moderation.
  - **Architect:** use when changing data boundaries or the exchange format. Must read `docs/architecture/federation.md`.

## 8. Decisions to make before rewriting

1. **Live P2P, CRDTs and ActivityPub.** Last session these were put "on the roadmap". If they stay, move them into a clearly labelled *Future direction* section so agents don't treat them as current requirements.
2. **Static HTML vs. JS rendering.** Either the generator should pre-render core content as HTML (a code change), or the rule should accept client-side rendering from bundled JSON.
3. **"Random Peer" link.** Implement it, or drop it from the rule.
4. **Third-party add-ons** (Google Analytics, AdSense, Giscus/Utterances, Tailwind CDN). Allowed as opt-in, or out of scope for a decentralization-first product?
5. **Sync cadence.** Manual only (current behaviour), or periodic while the app is open (as the mission says)?
6. **Webring ownership.** Is a hub file maintained by one member acceptable, or should ring membership be derived from members' own published files?
